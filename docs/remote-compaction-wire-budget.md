# remote compactionが要約後も413になる問題（Issue #124）

## 原因と修正

remote compactionはOpenAIのネイティブ圧縮形式を必要とするため、通常のDeepSeek要求とは別にOpenAIへ送る。その転送時には、Bridge専用の推論履歴（`cxb1:`）とBridgeの進捗表示itemを取り除く。

従来の実装では、要約境界の計画はこの転送形式で計測する一方、要約前後の最終判定にはBridge専用データを含む元の形式を使っていた。この不一致により、要約が完了し、転送するデータは上限内でもHTTP 413になった。同じ要約のcacheを再利用しても解消しなかった。

修正後は、remote compactionをネイティブ転送形式へ正規化してからすべての容量判定と要約境界の計画を行う。通常のDeepSeek会話の履歴やモデル選択は変更しない。上限の引き上げ、最新依頼・指示・未完了ツールの削除は行わない。OpenAI固有の暗号化reasoningは引き続き保持し、容量にも算入する。

Bridge専用の推論履歴だけで見かけの容量が増えている場合には、不要な追加要約も発生しなくなる。必要な要約とネイティブ圧縮のOpenAI通信をすべて削除する修正ではない。

## 検証

- 合成回帰: 修正前の要約完了後413、不要な追加要約を再現。修正後に成功することを確認。
- 指示・最新依頼・未完了ツール・OpenAI固有の暗号化reasoningの保持、実際に保護入力が上限を超えたときの拒否を確認。
- 障害のあった会話を隔離した一時CODEX_HOMEへコピーし、偽の認証情報とloopbackの模擬上流だけで入力を取得。自動圧縮の直前状態を再現した。元の会話は変更していない。
- 同じ入力に対する修正前のHTTP 413と修正後のHTTP 200を確認。要約入力の推定87956tokensは障害時ログの値と一致した。修正後のネイティブ圧縮入力は推定171095tokensで、16384tokensの出力予約を加えても200000tokens以内だった。
- 実Codex 0.164.0のapp-serverでも、会話コピーの圧縮完了、その後モデルを指定し直さずDeepSeekの模擬応答を受信するところまで確認した。
- 実API推論要求は0。実ユーザー本文・画像・認証情報は外部へ再送せず、Issueやリポジトリにも保存していない。模擬上流では実際のプロバイダーの稼働状況・課金・応答品質までは確認できない。

再現テストは `node --test test/model-router.test.mjs test/compaction-handoff.test.mjs test/handoff-status.test.mjs`。既存の `test/handoff-app-e2e.py` でもネイティブ圧縮後のモデル選択保持を検証できる。

## 利用中の会話

修正版が会話の接続先ルーターに反映された後は、同じ会話を再開して再試行できる。履歴削除や新規会話への移行は本修正のためには不要。目標が `Goal stalled` になっている場合は、再開操作 `/goal resume` を使う。

この修正は、実際に保護入力だけで上限を超える場合や、外部プロバイダーの障害まで成功させるものではない。その場合は履歴を保持して停止する。
